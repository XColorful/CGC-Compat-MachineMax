## 我查到的一个可疑点（但坐实不了）

## 找到的具体问题：不是开关的问题，是实现方式的问题

当前做法是把这个分裂载具的**所有**部件一次性置 `destroyed = true`，等它自己的 `preTick` 逐个走 `removePart`。

问题在于 `removePart` 的设计前提是"从一辆**还活着**的载具上拆走**一个**部件"——它每拆一个都会跑一次 `partNetSpiltCheck()`，**只要剩下的部件不再连通，就会再分裂出新载具**（`serverHandleSpilt` → `addSpiltVehicle`）。

于是"丢弃整辆车"会退化成级联：

```
拆 A → 剩余 B/C 断开 → 新建载具 V2 装 B、V3 装 C
     → compat 的 mixin 又把 V2/V3 登记进丢弃队列
     → 下一 tick 再拆 → 再分裂 → ...
```

结果一次脱落会反复新建 `VehicleCore`、迁移部件与子系统、拆掉再重建刚体与关节——而崩溃正好发生在物理层拆刚体那一刻。

对照着看更清楚：MachineMax **自己**正常摧毁部件是 `Part#onTick` 里按伤害把**单个**部件置 `destroyed`，一次一个，不会有这个问题。所以"一次性标记整辆车"是这个功能里唯一反常的地方。

## 改法：用 MachineMax 自己的整车销毁入口

`ObjectManager.removeVehicle()` → `VehicleCore.onRemoveFromLevel()` 就是 MachineMax 自己"这辆车没了"的入口（所有部件被拆光时它本来就这么收尾）。它**一次性**拆掉全部部件，不跑 `partNetSpiltCheck`，**不会分裂**。直接调它，级联就没了。

- `DetachedPartDiscard`：把"标记 destroyed"换成 `ObjectManager.removeVehicle(spiltVehicle)`。
- **仍然延后到 `LevelTickEvent.Post`**——这点必须保留：`addSpiltVehicle` 是在构造 `ConnectorDetachPayload` 的**实参**时被调用的，同步移除会让移除包早于分裂包发出，客户端状态分叉。原来的 javadoc 解释过这个，我照旧保留。
- 保留 `isRemoved` 判断：被合并掉的载具 `removeMergedVehicle` 也会置这个标志，能挡住重复移除。

## 加的排查日志

- `ObjectManagerMixin` 在 `removeVehicle` 头部加了一条：每次整车移除记录 uuid + 剩余部件数。**这条是给你排查用的关键**——物理崩溃只可能发生在拆载具前后，崩了回看日志就知道是不是紧跟一次批量拆除。
- `DetachedPartDiscard` 每次登记分裂载具记一条（uuid + 部件数 + 本 tick 第几个），并且**同一 tick 超过 2 个就打 WARN**——这正是级联的特征。
- 统计放在配置开关判断**之前**，所以就算哪天关掉开关，也能看出分裂有多频繁。
